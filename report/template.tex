\section{Introduction}
The Nano Bartender is an IoT system designed to classify beverages using a classifier model. Built upon the Arduino Nano 33 BLE Sense, the device leverages sensor fusion to analyze the optical and dielectric properties of liquids. Furthermore, it integrates a decoupled software architecture, utilizing Bluetooth Low Energy (BLE) to communicate with a Python-based web dashboard for real-time visualization of drink types and sip duration.

To guide the development of the "Nano Bartender," a set of specific requirements was defined during the initial design phase. These objectives ensured the device would be portable, responsive, and capable of distinguishing between beverages using sensor fusion.

\subsection{Functional Requirements}
The following functions were identified as critical for the system's operation:

\begin{itemize}
    \item \textbf{FR1 -- Sensor Acquisition:} The device shall read from the chosen sensors and produce stable digital measurements for processing.
    \item \textbf{FR2 -- Color-Based Drink Identification:} The device shall utilize the APDS-9960 sensor to detect and analyze the liquid's color. This serves as a primary filtering step to distinguish between visually distinct beverages (e.g., Wine vs. Beer) before analyzing dielectric properties.
    \item \textbf{FR3 -- Environmental Compensation:} The system aims to measure ambient or sample temperature to adjust estimation algorithms, compensating for temperature-dependent variations in sensor readings.
    \item \textbf{FR4 -- Connectivity:} The device must transmit results securely to a local host (PC or mobile application) via Bluetooth Low Energy (BLE) or Wi-Fi.
    \item \textbf{FR5 -- Power Management:} The firmware must support a fast boot sequence (ready to measure in $<10$ seconds) and include a low-power idle mode to conserve energy when not in use.
\end{itemize}

\subsection{Non-Functional Requirements}
To ensure usability and feasibility, the system must adhere to the following constraints:

\begin{itemize}
    \item \textbf{NFR1 -- Portability:} The device shall be handheld and battery-powered, targeting a battery life of $\geq 6$ hours of continuous use or $\geq 48$ hours of intermittent use, rechargeable via USB-C.
    \item \textbf{NFR2 -- Low Latency:} The total time from the user initiating a scan to the result being displayed on the dashboard shall be $\leq 5$ seconds.
    \item \textbf{NFR3 -- Cost Efficiency:} The Bill of Materials (BOM) should be kept under a target budget (e.g., €50–€80) to ensure the device remains affordable for student-grade projects.
\end{itemize}

\section{System Design \& Integration}

The system logic is divided into two distinct operational modes triggered by user interaction.

\subsection{Data Acquisition \& Pre-processing Strategy}
To ensure reliable data for classification, raw sensor values are not used directly. Instead, a buffering and normalization strategy is implemented:

\begin{itemize}
    \item \textbf{Sliding Window:} The system collects a buffer of 5 consecutive readings (\texttt{MAX\_READINGS}) for both the Capacitive Sensor and the RGB Color Sensor.
    \item \textbf{Averaging:} These values are averaged to reduce signal noise and outliers.
    \item \textbf{RGB Normalization:} To mitigate the effects of ambient light intensity, raw RGB values are converted to chromaticity ratios. For a given channel $C \in \{R, G, B\}$, the input feature $C'$ is calculated as:
    \begin{equation}
        C' = \frac{C}{R + G + B}
    \end{equation}
    This ensures the model learns the \textit{color} of the liquid rather than the brightness.
\end{itemize}

\subsection{Sip Detection Algorithm (Finite State Machine)}
When in "Drinking Mode," a Finite State Machine (FSM) uses the gyroscope and accelerometer to track gestures. The system cycles through four states:

\begin{enumerate}
    \item \textbf{IDLE:} The system waits for rotational velocity on the X-axis ($G_x$) to exceed the \texttt{GYRO\_LIFT\_TRIGGER} ($40.0$ deg/s).
    \item \textbf{LIFTING:} The system monitors stability. If angular velocity drops below \texttt{GYRO\_QUIET} ($10.0$ deg/s) and the Y-axis accelerometer ($A_y$) exceeds \texttt{ACCEL\_TILT\_THRESH} ($0.60$ g), the system transitions to \texttt{AT\_MOUTH} and records the start time.
    \item \textbf{AT\_MOUTH:} The device is currently tilted. The system waits for the user to lower the glass, defined as $G_x$ dropping below \texttt{GYRO\_LOWER\_TRIGGER} ($-40.0$ deg/s).
    \item \textbf{LOWERING:} Once motion stabilizes, the total duration is calculated and transmitted via BLE with the "SIP:" prefix.
\end{enumerate}

\section{Software Architecture}
The host-side application implements a decoupled, three-tier architecture to handle asynchronous Bluetooth data and synchronous user interface rendering.

\subsection{BLE Bridge (Middleware)}
The \texttt{ble\_bridge.py} script acts as the gateway between the embedded device and the server. It utilizes the \texttt{Bleak} library to manage the connection asynchronously.
\begin{itemize}
    \item \textbf{Connection:} Connects to service UUID \texttt{19B10000...} and subscribes to notifications.
    \item \textbf{Protocol Parsing:} It handles three data types:
    \begin{enumerate}
        \item Mode Switches ("MODE:")
        \item Sip Duration events ("SIP:")
        \item Classification results ("LABEL,SCORE")
    \end{enumerate}
    \item \textbf{API Forwarding:} Parsed data is immediately POSTed to the Backend API.
\end{itemize}

\subsection{Backend API (State Store)}
Built with \texttt{FastAPI} (\texttt{api.py}), this component serves as a thread-safe in-memory state store. It decouples the real-time constraints of the BLE connection from the polling frequency of the frontend.
\begin{itemize}
    \item \textbf{Endpoints:} Exposes \texttt{/update}, \texttt{/update-sip}, and \texttt{/update-mode} for the bridge, and corresponding GET endpoints for the frontend.
    \item \textbf{Data Models:} Uses Pydantic models (\texttt{DrinkData}, \texttt{SipData}) to validate incoming payloads.
\end{itemize}

\subsection{Frontend (User Interface)}
The user interface is developed using \texttt{Streamlit} (\texttt{frontend.py}). It polls the API every 0.5 seconds to refresh the visual state without blocking application logic.
\begin{itemize}
    \item \textbf{Visual Feedback:} Renders dynamic cards for drinks (Water, Beer, Wine, Aperol, Rum) and displays a progress bar for classification confidence.

\section{Machine Learning Implementation}
The core intelligence of the "Nano Bartender" is a classifier trained using \textbf{Edge Impulse}.

\textbf{Dataset Creation:}
\begin{itemize}
    \item \textbf{Classes:} Water, Beer, Wine, Aperol, Rum.
    \item \textbf{Features:} Capacitance (Analog Value), Red, Green, Blue (Color Channels).
    \item \textbf{Model Architecture:} A Neural Network classifier was designed to take the 4 input features and output a probability distribution across the 5 classes.
    \item \textbf{Deployment:} The trained model was exported as an Arduino library \\
    (\texttt{DrinkAlyzer\_inferencing.h}) and deployed directly to the Nano 33 BLE Sense, allowing for offline, low-latency inference.
\end{itemize}

\section{Design Choices}
This section outlines the critical architectural and methodological decisions made during the development of the "Nano Bartender".

\subsection{Sensor Selection and Exclusion: The DS18B20}
Initially, the hardware design included a DS18B20 digital temperature sensor (Figure~\ref{fig:ds18b20}). The hypothesis was that liquid temperature might alter dielectric properties. However, we excluded this sensor because:
\begin{enumerate}
    \item \textbf{Incompatibility:} Significant library conflicts arose between the OneWire protocol and the nRF52840 architecture of the Nano 33 BLE Sense.
    \item \textbf{Lack of Correlation:} Empirical testing revealed that for typical drinking temperatures, the variation in temperature did not produce statistically significant changes in capacitive values.
\end{enumerate}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\textwidth]{images/ds18b20.png}
    \caption{DS18B20 Digital Temperature Sensor}

\end{figure}

\subsection{Feature Engineering: RGB Ratios vs. Raw Values}
A crucial design choice was made regarding color data processing. Instead of feeding raw integer counts from the APDS-9960 directly into the neural network, we used ratios relative to total light intensity.

\textbf{Reasoning:} Raw values are highly susceptible to ambient light conditions and sensor distance. Ratios focus on the chromaticity of the liquid, making the classifier robust to environmental changes.

\subsection{Goal: Discrete Classification vs. Mixture Analysis}
The original objective was to analyze the composition of mixed drinks (e.g., percentages). We pivoted to discrete classification (identifying pure liquids) due to hardware limitations:
\begin{itemize}
    \item \textbf{Sensor Sensitivity:} The standard Capacitive Soil Moisture Sensor lacks the resolution to detect minute changes in dielectric constants caused by small mixture variations.
    \item \textbf{Data Collection:} Training a classifier for percentages would require an unfeasible amount of data to cover all permutations.
\end{itemize}

\section{Results \& Evaluation}
The system was evaluated in a real-world setting to assess both the classification accuracy of the model and the reliability of the sip detection algorithm.

\subsection{Classification Performance}
The Edge Impulse model, demonstrated high reliability in distinguishing between the five target beverages.
\begin{itemize}
    \item \textbf{High Confidence:} For the liquids the model consistently returned confidence scores above 80\%.
    \item \textbf{Inference Speed:} The inference time on the Nano 33 BLE Sense was negligible ($<20$ms), allowing for real-time responsiveness without blocking the main loop.
\end{itemize}

\subsection{Sip Detection Reliability}
The gyroscope-based Finite State Machine proved effective in tracking natural drinking gestures.
\begin{itemize}
    \item \textbf{False Positive Rejection:} The inclusion of the \texttt{GYRO\_QUIET} threshold prevented accidental bumps or table vibrations from triggering a "Sip" event.
    \item \textbf{Duration Accuracy:} The system successfully recorded sip durations ranging from short tastings (0.5s) to longer consumptions (3.0s+), transmitting the data to the Python backend with minimal latency.
\end{itemize}

\subsection{System Latency}
The end-to-end latency—from a physical change in the liquid to the visual update on the web dashboard—was estimated to be under 500ms. This includes:
\begin{enumerate}
    \item Sensor reading and inference on the Arduino.
    \item BLE transmission to the Python Bridge.
    \item API processing and frontend polling.
\end{enumerate}
This near real-time performance validates the choice of the decoupled, asynchronous software architecture.

\section{Conclusion}
The "Nano Bartender" demonstrates that it is possible to build an intelligent drink tracker using low-cost hardware. 

By combining a color sensor with a capacitive sensor, our system successfully identifies five different beverages: Water, Beer, Wine, Aperol, and Rum.

We successfully integrated the Arduino Nano 33 BLE Sense with a modern web application. The system processes sensor data directly on the device and wirelessly transmits the results to a laptop, where a dashboard displays the drink type and sip duration in real-time. The software design proved reliable, ensuring that the user interface updates smoothly without connection lags.
